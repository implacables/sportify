## YOLO Phase B: fine-tuning yolo26m on SoccerNet

### Context
Phase A (pretrained COCO weights) left us at mAP@0.5=0.910, 33.7 FPS on RTX 3090.
Goal: fine-tune on SoccerNet broadcast footage and see if accuracy and/or speed improve.

### Data situation
The SoccerNet `train` split (57 clips) was never downloaded — only the `valid` split (58 clips) is on disk. Split the valid clips manually:
- **Train**: 55 clips (all valid except the 3 established bench clips)
- **Val/bench (held out)**: SNGS-021, SNGS-022, SNGS-023

Not ideal — both sets come from the same SoccerNet `valid` distribution, so results are likely a bit optimistic compared to a true train/val split. Worth noting when interpreting numbers.

### What was built
- Added `--yolo-split` flag to `convert_to_yolo.py` so valid clips can be written to `images/train/` instead of `images/val/`
- Wrote `run-train.sh` — mirrors the style of `run-eval.sh` / `run-bench.sh`, saves result JSON to `benchmarks/results/yolo-soccernet/<timestamp>-train/`
- Wrote `watch-train.sh` — tails `results.csv` live and writes a formatted per-epoch markdown table with Δ vs Phase A baseline to `benchmarks/results/yolo-soccernet/training-progress-<run-name>.md`

### Training run: yolo26m-finetune-v1
- Init weights: `yolo26m.pt` (COCO pretrained)
- 50 epochs max, patience=10, batch=16, imgsz=640, RTX 3090
- Hit disk quota trying `cache="disk"` (per-user quota, not actual disk full — 403 TB available)
- Switched to `cache="ram"`:
  - Cache load: 40,873 images → 26.3 GB RAM in 2 min 22 sec
  - GPU utilization jumped from 68% → 99%
  - Epoch time: **18.7 min → 12.4 min** (3.5 it/s vs 2.3 it/s), ~34% faster
- Early stopping triggered at epoch 17 (no improvement for 10 epochs from best at epoch 16)

## Walking skeleton: detection + tracking pipeline

### What was built

First real pipeline code under `sportify-game-reconstruction/src/`:

```
src/
├── pipeline.py              ← entry point
├── requirements.txt
├── trackers/
│   └── bytetrack.yaml       ← explicit ByteTrack config
└── jobs/
    └── dev-sngs021.yaml     ← dev job descriptor
```

Entry point: `python pipeline.py --job jobs/dev-sngs021.yaml`

Reads a YAML job descriptor → decodes video with frame stride → runs YOLO detection + ByteTrack → writes `reconstruction.json` and `job.meta.json` with per-step timing.

### Test video

SoccerNet clips are JPEG image sequences, not MP4s. Synthesised a test clip for pipeline input:

```bash
ffmpeg -framerate 25 -i SoccerNetGS/valid/SNGS-021/img1/%06d.jpg \
  -c:v libx264 -pix_fmt yuv420p -crf 18 \
  SoccerNetGS-synth-clips/sngs-021.mp4
```

Stored at `/workspace/SoccerNetGS-synth-clips/sngs-021.mp4` (H.264, 1920×1080, 25 fps, 750 frames, ~77 MB). Job descriptor uses this as `input.video_path`.

### Tracker

ByteTrack via Ultralytics `model.track(persist=True)`. Copied the default config into `src/trackers/bytetrack.yaml` so parameters are owned and visible. Key setting to note: `track_buffer: 30` processed frames × `stride: 5` = 150 actual frames = 6 s of occlusion tolerance.

### Per-step benchmark — RTX 3090, pretrained yolo26m.pt, stride=5

| Step | Mean ms/frame |
|------|-------------:|
| Video decode | 2.24 ms |
| YOLO preprocess | 1.49 ms |
| YOLO inference | 11.29 ms |
| YOLO postprocess | 0.52 ms |
| **ByteTrack association** | **20.43 ms** |
| Projection (stub) | ~0 ms |
| **Total** | **~33.7 ms → 26.8 fps** |

ByteTrack dominates at 61% of per-frame budget. It is CPU-bound (pure numpy) regardless of GPU. YOLO inference is GPU-accelerated at 11 ms.

**26.8 fps end-to-end** (detection + tracking) vs SoccerNet baseline ~1.1 fps — **~24× faster** before any optimisation. Model is still pretrained COCO weights; fine-tuned `best.pt` has not been promoted yet.

### Finding: ByteTrack is CPU-bound and a throughput bottleneck

ByteTrack dominates the per-frame budget at 20.43 ms (61%) while YOLO inference on GPU sits at 11.29 ms (33%). The gap will widen as YOLO gets faster with the fine-tuned model — ByteTrack does not benefit from the GPU at all.

ByteTrack is pure numpy/scipy — all association (IoU matrix, Hungarian matching, Kalman filter updates) runs on CPU. This is an architectural ceiling: no matter how fast inference gets, the tracker caps throughput at roughly 1000 ms / 20 ms = ~50 fps, and that ceiling drops as more detections appear per frame (SNGS-021 averages ~18 detections/frame).

For a throughput-optimised pipeline this is not ideal. Alternatives to investigate:

| Tracker | GPU? | Notes |
|---------|------|-------|
| ByteTrack (current) | No | Fast enough for now; ceiling ~50 fps at 18 det/frame |
| BoT-SORT | No | Adds ReID branch — heavier, not a throughput win |
| OC-SORT | No | CPU-bound like ByteTrack; similar speed profile |
| SORT (vanilla) | No | Lighter than ByteTrack; lower re-ID recovery |
| Custom IoU tracker | No | Trivial to implement; no Kalman, no lost-track buffer — worth profiling |

Not a blocker for the POC — 26.8 fps already clears the SoccerNet baseline by 24×. Revisit tracker choice if throughput headroom tightens after identity association (ReID + OCR) is wired in.
